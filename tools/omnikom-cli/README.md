# omnikom: the platform CLI (slice 1)

Spec: `docs/blueprint/26-PLATFORM-CLI.md`. One Node 20+ program, no dependencies, `psql` on the path.
`node tools/omnikom-cli/omnikom.mjs <command> [--target local|staging|production] [--as <identity>] [--expect <code>] [--json]`
Every command prints ONE JSON object `{ ok, command, target, code, expect?, matched?, exit, data }`. Exit: 0 matched, 1 not, 2 usage, 3 BLOCKED.
`--expect` takes the HTTP status (`202`) or the platform code (`S-NOT-FOUND`, `S-OWN-ONLY`, `I-UNKNOWN`...); `ok` is the success code of SQL commands.
Targets read variables by NAME: `STAGING_DB_URL STAGING_SUPABASE_REF ..._SECRET_KEY ..._PUBLISHABLE_KEY`, the `PROD_` set, `LOCAL_DB_URL` (this machine only), `LOCAL_FUNCTIONS_BASE`. Default target: local.
Secrets never leave the program: stdout and stderr pass `lib/redact.mjs`; psql gets its connection through `PG*` variables, never argv.

| Command | What it does |
|---|---|
| `status` | reachable, migrations applied/pending/changed (ledger vs files), functions deployed, key variables present (names, booleans) |
| `apply [--dry-run]` | `supabase/apply-staging.mjs` on the target (`--i-mean-production` on production) |
| `test walls` | `supabase/tests/run-staging.mjs` (tenancy tests, rolled back); refuses a database that holds the seeded fixtures |
| `seed test [--alert-to email] [--clean]` | workspaces A and B, sites, contracts, 5 test logins (the `tenancy.test.sql` fixtures); twice changes nothing |
| `seed workspace --slug --name --industry --deploy-target --preview-host --contract f` (or `--plan dir --entities f`) | a real client from a `contracts/from-plan.mjs` contract: workspace, site, contract, pages, places (SQL path) |
| `key mint --site s` / `key list` / `key revoke --id` | site signing key into Vault + registry + the env file named by `OMNIKOM_ENV_FILE`; never a value in output. The number `n` of `site-<slug>-key-<n>` is one more than the highest in the Vault, the registry (revoked rows too) and the env file's record line `# site-<slug>-key-<n>: ...` (the env file survives `seed test --clean`); `--n` overrides. A mint REWRITES the env file: one record line and one value line per variable (earlier ones and duplicates removed, the new two where the first stood, or at the end after a blank line), other lines byte for byte, CRLF kept, temp file and rename. A Vault name collision is the SQL error (exit 1) |
| `contract validate --file f` / `contract place --file f --rows r` | `contracts/validate.mjs`, `place.mjs` |
| `lead send --site s [--form f] [--fixture f] [--retry] [--key uuid]` | a signed lead to `capture-lead`; `--retry` resends the same key and counts rows |
| `lead list/get/update/add/delete --as person` | reads as `authenticated` with the person's claims (RLS), writes through `service.*` |
| `content save/get/history --as person` | contract_for + validator + `service.save_as`; reads through RLS |
| `publish --as person --site s --rows ids`, `job get/wait/set` | `service.start_publish`; `job set` stands in for the runner on the SQL path |
| `verify --only lead` | 16 checks of `capture-lead` over HTTP, one PASS/FAIL line each on stderr, exit 1 on any FAIL. Includes the ledgers of migration 7, counted read-only before and after: each refused signature adds one `security_events` row (`bad-signature`), a paused site answers 409 and adds one `suspended` row, an accepted lead has exactly one `consent_ledger` row and a retry of the same key adds none. Both ledgers are append-only, so a run leaves its rows behind |
| `verify --only walls` | 5 checks of the Data API as anon (service functions refused, leads / key registry / sites give nothing); needs only the publishable key. Person checks are listed under `waiting` |
| `verify --only people` | 15 checks of what each seeded login sees through the Data API with its own session (owner B reads A's leads: 0, member A1 only their own, nobody none, keys hidden, staff only at aal2; an owner cannot update a lead directly); makes two leads and removes them |
| `audit --dir <folder> [--json] [--only ids]` | `tools/audit` over a built folder: the engine's lines unchanged (`PASS`/`WARN`/`FAIL`/`SKIP <rule> <page>...`), then `audit: <pages> pages, <rules> rules, <n> FAIL, <n> WARN, <n> SKIP`. Exit 0 no FAIL, 1 a FAIL, 2 usage (no `--dir`, missing folder, unknown rule id, `--target`, `--expect`) or a crash (`ERROR audit crashed: ...`). No target, no network, writes nothing. `--json` prints the usual object (`data` is the engine's result) |
| `gate --dir <folder> [--json]` | the publish gate: every rule, no `--only`. Prints `GATE PASS <pages> pages, <rules> rules` or `GATE FAIL <n> finding(s)` and the FAIL lines. Same exits as `audit`; a deploy runs after exit 0 only. `--json` data is `{ pass, exit, fails, pages, rules }` |
| `tools ensure [--only a,b]` / `tools list` | the binaries the checks need (DECISIONS 42), from `tools.json`, into the git-ignored `<repo>/.tools/` (`OMNIKOM_TOOLS_DIR` moves it, tests only). No target. `ensure` refuses before any byte is fetched: a url that is not an asset of `https://github.com/<repo>/releases/download/v<version>/`, a release younger than 7 days (supply-chain rule 1), a missing sha256 or size. After the download and before extraction the size and sha256 must equal the manifest's, or the file is deleted and the command exits 1 naming the tool with the expected and actual hash (printed as `first16...last8`: the redaction masks a full 64-digit hex). Extraction is the system tar only (`%SystemRoot%\System32\tar.exe`, which reads zip; `tar` on linux, which cannot read the zip of deno), into a temp folder inside `.tools/`, then a rename; the executable is copied to `.tools/bin/`. A `.ok` file (version, archive sha256, executable sha256) makes a second run fetch nothing. No install script, no PATH change. `node` is checked, never downloaded (`--only node`). Result per tool: `present`, `downloaded` or `refused` with the reason; exit 0 only when every requested tool is present or downloaded. `list` prints the manifest and what `.tools/` holds (read-only) |
| `ci [--job <id>] [--root <dir>] [--install] [--json]` | every job of `.github/workflows/ci.yml`, in file order, locally, with those binaries (`.tools/bin` first on the CHILD's PATH only). One line per job `PASS|FAIL <id>  <last line>` (the failing step's last line; redacted), then `ci: <n> jobs, <p> PASS, <f> FAIL`; exit 0 all PASS, 1 any FAIL, 2 usage (unknown `--job`, `--target`, `--expect`). `--root` runs the jobs against another checkout; `--json` adds every step. See "How ci maps ci.yml" below |
| `mfa enroll-staff` | once: a TOTP factor for the staff test login, its secret to the env file as `TEST_STAFF_TOTP_SECRET` (never printed) |

Identities: `owner-a owner-b member-a1 member-a2 staff nobody` (claims on the SQL path), `site:<slug>` (`SITE_SIGNING_KEY_<SLUG>`), `runner` (`RUNNER_KEY`), `cron` (`CRON_SECRET`).
Production runs only `status` (read-only connection) and `apply --i-mean-production`; every other command is refused (exit 3) before anything is spawned.
Fixtures live in `fixtures/` and are synthetic (example.com, 555); anything else needs `--real` and prints a warning.

## Live parts: proven, waiting, blocked
- **Person sessions over HTTP**: PROVEN on staging 2026-10-30 (`lib/identity.mjs personToken`: Auth admin `generate_link` for the login's email, then `/verify` with the token hash; in memory only, masked in all output). `seed test` writes the six logins the way GoTrue reads them (aud, role, instance, confirmed, empty token columns; earlier rows are repaired by one run). Before that, two approaches failed on `(id, email)`-only rows. `staff` is brought to aal2 with a TOTP factor: `omnikom mfa enroll-staff` (once) puts `TEST_STAFF_TOTP_SECRET` in the env file; without it the staff checks are listed as waiting.
- **Waiting, not faked** (they need functions slice 2 builds): member A1 updates A2's lead (S-NOT-FOUND), member A1 publishes A2's listing (S-OWN-ONLY), a member adds a lead for someone else.
- **`lead send` / `verify --only lead` against the deployed function**: the model of `capture-lead` (`test/harness.mjs`) reads keys the way the function does (`service.active_key` joined to the Vault view), but the deployed run belongs to the step 2 session. `key mint` and `seed test` were observed working on staging (the `(id, email)` insert and `vault.create_secret` through the pooler).
- Slice 2 (function paths for save, publish, export, job callback, lead update, add lead) and slice 3 (`onboard`) are not built.

## How ci maps ci.yml
ci.yml is read by a small reader for this file's shape (`parseWorkflow` in `commands/ci.mjs`; no YAML dependency). Every step is mapped BY NAME in the table `ROWS` to its local action:
- `uses: actions/checkout` is "the working tree" (the line says so); `setup-node` and `setup-deno` are a version check (`node --version`, `.tools/bin/deno --version`) against ci.yml's and the manifest's version.
- the PostgreSQL PATH step is "`initdb` found" (it must be on the PATH, as the CLI's own tests need it); the `df` steps report disk and memory.
- `run: node ...` steps run the same command line through the running node (one command line, no shell syntax: a `&&` or a pipe in such a step FAILs the job instead of being half-run).
- `curl ... sha256sum ... tar` download steps become `tools ensure --only <tool>`, after checking that the step's version, url and sha256 equal the manifest's linux entry; the later `"$RUNNER_TEMP/<tool>/<tool>"` call becomes `.tools/bin/<tool>` with the same arguments (a glob like `.github/workflows/*.yml` is expanded by the runner, sorted). actionlint always gets `-shellcheck .tools/bin/shellcheck` given explicitly (before the file arguments), the shellcheck version is checked against the manifest, and the job's line ends with `[shellcheck <version>]`.
- `npm ci ...` runs as written only with `--install`; without it the step is SKIP (PASS) when `factory/runner/node_modules` exists and FAIL ("run with --install") when it does not.
- A step the table does not map, a step key the reader does not model (`env:`, `shell:`, `continue-on-error:`...), an `if:` other than `always()`, a job key other than name, runs-on, timeout-minutes and steps, or a top-level key other than name, on, permissions, concurrency and jobs, FAILs: ci.yml cannot grow a check this command skips. A rename of a mapped step is the same failure on purpose (the platform department then updates the table here).
- A step after a failed step is SKIP unless it has `if: always()`. Each command gets the job's `timeout-minutes` as its time limit, never less.
- stdout and stderr are captured separately: a failing command's last line is the last line of its stderr when it printed any.

## Tests
`tools.json` and ci.yml agree (a test with its own regular expressions fails when a version, linux url, sha256, `node-version` or `deno-version` differs); `tools ensure` and `ci` are tested over a fake fetch and fixture archives built with the system tar, with a fake spawn that records the tools' calls: no network and no real download. The real ci.yml is run through `ci --install` with every command faked, to prove that every step of it is mapped today.
`node tools/omnikom-cli/test/run.mjs [--unit|--db]` (units + a throwaway cluster; the cluster takes minutes to start on this machine) and `node tools/omnikom-cli/test/mutate.mjs` (one rule removed per mutant, all must go red).
